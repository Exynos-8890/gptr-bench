# gptr 临床分析工作流的初步性能实验

## 1. Introduction：实验目的

临床数据分析通常需要连续修改：先检查队列，再建立模型，随后增加协变量或调整分析条件。AI agent 完成这类任务时，既要生成正确代码，也要在多轮请求之间管理数据与分析状态。gptr 的设计是让 agent 在常驻 R 会话中工作，前一步创建的数据和模型可以供后一步继续使用。另一种常见方式是由 coding agent 调用 shell 和 Rscript，通过文件保存并传递结果。

本实验比较这两种方式完成同一临床工作流时的正确性、耗时和内存使用，同时设置固定计算步骤的离线对照。首轮先回答三个问题：完整任务能否正确完成；真实模型参与时两条路径表现如何；去掉真实模型调用后，不同执行方式的耗时是多少。

实验材料集中在 `dev/bench/biomedical/`，下文的链接均以该目录为起点。整体设计见 [plan.md](../../v0.3/plan.md)，运行入口和使用说明见 [README.md](../../README.md)。本轮仅完成临床生存分析，其他生物医学任务留待后续扩展。

## 2. Methods：任务与实验设计

### 2.1 一个包含三次请求的分析任务

小数据实验使用 `survival::veteran`，共有 137 条记录，其中 128 个事件。一次完整实验依次接收三个请求，模拟用户在初步分析后继续修改模型的过程。

第一步检查队列，处理分析变量的缺失值，检查生存时间及事件状态，输出 `qc.csv`。第二步按治疗组计算 Kaplan–Meier 生存曲线，拟合包含治疗组和年龄的 Cox 模型，输出 `km.csv` 和 `cox.csv`。第三步沿用同一队列，在 Cox 模型中加入反映患者功能状态的 Karnofsky 评分，输出 `revised.csv`。

任务定义位于 [tasks/clinical.R](../../tasks/clinical.R)，其中集中保存数据准备方法、三个请求以及离线对照所用的固定计算步骤。这样，任务要求与具体执行方式可以分开维护。小数据实验的整理结果位于 [reports/clinical-pilot/](../results/clinical-pilot/)，原始执行记录位于 [runs/clinical-pilot/](../../runs/clinical-pilot/)。

### 2.2 五个实验组

实验分为真实模型执行和离线执行两部分。真实组让模型自行完成任务；离线组提供既定的 R 操作，不再请求真实模型。

| 组别 | 执行方式 | 主要用途 |
|---|---|---|
| A1：真实 gptr | 模型通过 gptr 操作常驻 R 会话 | 观察完整 gptr 工作流 |
| C1：真实 Codex | 模型通过 shell、Rscript 和文件完成任务 | 观察普通 coding agent 工作流 |
| A2：gptr 回放 | fake provider 驱动实际 gptr 循环 | 观察固定操作在 gptr 中的执行表现 |
| C2：RDS 回放 | 每一步启动新 R 进程，用 RDS 传递所需对象 | 观察分步执行和状态读写的表现 |
| C3：单进程 Rscript | 一个 R 进程连续完成全部计算 | 提供批量执行基线 |

A1、C1 使用相同的 Codex CLI 0.165.0 和 `gpt-6-sol` 模型，沿用模型默认推理设置。每组独立运行三次，每次的三个请求延续同一个 agent 会话。两组按轮次交错执行顺序，所有实验串行运行。对应记录为 [runs/clinical-pilot/](../../runs/clinical-pilot/) 下的 `A1-1` 至 `A1-3`、`C1-1` 至 `C1-3`；末尾数字表示重复编号。

固定步骤对照中，A2、C2、C3 执行相同的预设计算，每组重复十次，记录在同一目录下的 `A2-*`、`C2-*`、`C3-*` 子目录。A2 使用的 fake provider 会按脚本提供预先确定的工具调用，使真实 gptr 执行循环仍然参与运行。

另设真实轨迹回放：捕获三次 A1 实际执行的 R 操作，先在干净环境中验证计算结果，再转换为 fake provider 输入，每条轨迹回放十次。这部分记录分别放在 [trajectory-1/](../../runs/clinical-pilot/trajectory-1/)、[trajectory-2/](../../runs/clinical-pilot/trajectory-2/) 和 [trajectory-3/](../../runs/clinical-pilot/trajectory-3/)。其中 `capture/` 保存验证和转换材料，`A2-*` 保存各次回放。它与预设步骤对照的区别，在于计算代码来自真实 agent 的执行过程。

这些分组对应两种实际使用情形。真实组中，用户只给出分析要求，模型决定调用哪些工具、怎样组织代码以及是否需要修正。离线组中，操作已经确定，比较的是同一批计算通过不同路径运行的表现。因此，真实组允许模型采用不同实现，只要最后的分析产物满足相同要求；固定步骤对照则统一代码，使执行方式成为更明确的比较对象。

本轮对所选分析对象采用能够通过 RDS 保存和恢复的假设。C2 每步读取所需状态并写出后续使用的对象；C3 将步骤连在一起；A2 保留常驻会话并经过 gptr 的执行循环。这三条路径都完成同一份分析，但组织计算的方式不同。

### 2.3 正确性与测量口径

独立检查器 [evaluate.R](../../evaluate.R) 重新计算参考结果，核对四份输出表的列结构及数值，容差为 `1e-6`，允许不影响结果的行顺序变化。生存曲线必须包含各治疗组全部唯一观测时间，包括只有删失、没有事件发生的时间点。完成运行并不等于成功，产物通过检查才计为正确。

耗时从执行开始计到任务完成，包括启动、首次加载、权限处理和正常 agent 开销；数据准备和事后正确性检查不计入。内存按约 20 毫秒间隔采样进程树 RSS，再报告各次采样峰值的中位数。每次实验使用独立工作目录，避免上一次的结果直接影响下一次。

编排由 [run.py](../../run.py) 负责，包括选择分组、重复执行、采样、捕获轨迹和汇总报告；[runner.R](../../runner.R) 负责 R 端的数据准备及不同执行路径。二者共同调用任务定义和检查器。

## 3. Results：实验结果

### 3.1 小数据实验

本节结果见 [clinical-pilot/report.md](../results/clinical-pilot/report.md)，逐次测量见同目录的 [summary.csv](../results/clinical-pilot/summary.csv)。真实组与固定步骤对照的结果如下。

| 组别 | 正确次数 | 耗时中位数（秒） | 采样内存峰值中位数（MiB） |
|---|---:|---:|---:|
| A1：真实 gptr | 3/3 | 47.96 | 920.6 |
| C1：真实 Codex | 3/3 | 69.02 | 485.9 |
| A2：固定步骤 gptr 回放 | 10/10 | 8.07 | 465.9 |
| C2：固定步骤 RDS 回放 | 10/10 | 2.01 | 172.8 |
| C3：固定步骤单进程执行 | 10/10 | 0.83 | 172.1 |

两组真实执行均完成了全部任务。A1 耗时范围为 45.81—50.07 秒，C1 为 60.10—73.01 秒；A1 的耗时中位数低约 31%，采样内存峰值则更高。固定步骤对照中，单进程 Rscript 最快，RDS 回放其次，gptr 回放耗时最长。

真实轨迹回放的三组耗时中位数分别为 8.34、7.83 和 7.64 秒，三十次全部正确。整理后的三条轨迹位于 [reports/clinical-pilot/](../results/clinical-pilot/) 中的 `trace-a1-1.jsonl` 至 `trace-a1-3.jsonl`，可以用于离线复现；`trace-index.json` 记录轨迹来源及校验信息。这部分结果验证了“先确认计算正确，再转换并回放”的流程。

真实轨迹与固定步骤的结果分别保留，避免混淆两种回放。前者回答模型实际生成的操作能否重新执行，后者方便在统一计算内容下比较执行路径。当前转换保留的是观察到的 R 操作，fake provider 会重新组织这些操作的回复，并不复原 Codex 内部的全部请求过程。普通 Codex 组的命令和输出也有记录，但本轮没有把它们自动转换为可回放轨迹。

### 3.2 十万行合成数据实验

为检查较大输入下的执行流程，我们生成十万行合成队列，包含治疗组、年龄、Karnofsky 评分、生存时间和删失信息，固定随机种子以便重复生成。数据构造仍定义在 [tasks/clinical.R](../../tasks/clinical.R)，输入 RDS 约为 3.2 MB。本实验仅运行三个离线组，每组一次。

| 组别 | 正确次数 | 单次耗时（秒） |
|---|---:|---:|
| A2：gptr 回放 | 1/1 | 8.12 |
| C2：RDS 回放 | 1/1 | 2.56 |
| C3：单进程 Rscript | 1/1 | 1.51 |

三个组均通过检查，耗时排序与小数据一致。报告位于 [reports/clinical-synthetic-100000/](../results/clinical-synthetic-100000/)，原始记录位于 [runs/clinical-synthetic-100000/](../../runs/clinical-synthetic-100000/)，其中 `A2-1`、`C2-1`、`C3-1` 对应表中的三次执行。

### 3.3 如何阅读结果文件

上述两个报告目录采用相同结构：`report.md` 是便于阅读的结果表，`summary.csv` 保存逐次运行指标，`manifest.json` 记录输入校验值、源码标识和环境信息，`wall-time.png` 与 `wall-time.svg` 展示耗时。只看主要结果时阅读报告；检查某一次执行或重新作图时使用 CSV；核对实验条件时查看 manifest。

`runs/` 保存更完整的运行材料，包括执行轨迹、检查结果和状态文件；其中 `prepared/` 保存该轮准备好的输入。轨迹中的 R 调用可用于追查分析步骤，检查结果用于判断失败来自计算结果还是输出格式。整理报告与原始记录通过实验名称和重复编号对应。

如果要从结果追溯到实现，可以按“报告、原始记录、任务代码、检查器”的顺序阅读。例如，小数据表中某次运行出现异常，先在 CSV 中找到组别和编号，再进入相应运行目录查看轨迹及检查结果，最后对照任务要求判断原因。若只是了解实验设计和结论，无需阅读每次调用日志。

整个目录的分工也由此明确：`tasks/` 决定做什么分析，两个执行入口决定怎样运行，检查器决定结果是否合格，`reports/` 呈现比较结果，`runs/` 提供追溯依据，`tests/` 验证实验工具自身。后续增加任务时，可以沿用这一组织方式，把新的任务定义和判定规则接入已有流程。

## 4. Discussion：当前结论与下一步

正式报告合计 69 次执行：六次真实模型实验、三十次固定步骤对照、三十次真实轨迹回放，以及三次合成数据实验，全部通过独立检查。当前已经建立了真实执行、产物检查、轨迹捕获、验证转换和离线回放的完整链路。

本轮观察到，gptr 在选定任务上的真实执行耗时较低；固定计算步骤时，单进程 Rscript 的耗时最低。两个结果分别描述完整 agent 工作流和既定代码执行过程，应结合各自的实验条件阅读。本轮还没有展示大数据场景下的性能优势。

目前只覆盖一个任务、一个模型和一台机器，真实组每组仅三次。十万行输入也只有约 3.2 MB，每组只执行一次，主要用于确认规模参数和流程可以工作。重复回放可以观察同一轨迹的运行波动，但不能替代更多独立模型实验。内存结果是采样 RSS，适合比较本轮观测值，不代表精确的独占内存峰值。

正式实验前曾发现生存曲线输出要求不够明确，两组提示统一补充删失时间点要求后才开始上述试验。早期诊断记录保留在 [runs/pilot-smoke/](../../runs/pilot-smoke/)，未计入正式的 69 次执行。

实验工具本身的验证放在 [tests/](../../tests/)：`test-clinical.R` 检查任务与结果判定，`test_runner.py` 检查离线执行路径，`test_capture.py` 检查轨迹验证和转换，包括错误轨迹被拒绝的情况。下一步可沿用现有任务、执行和评估结构，优先增加数据规模及真实重复次数，再扩展其他生物医学任务与模型。
