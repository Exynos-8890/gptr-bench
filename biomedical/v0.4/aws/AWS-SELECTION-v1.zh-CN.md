## A 申请结论：一台小核心、大内存机器

```callout ok 推荐申请 x8i.2xlarge 一台
8 vCPU对应4个物理核心，内存128 GiB。
首轮申请14天，AWS预算500美元。
机器、磁盘及一个公网IPv4的基础估算为378.31美元。
```

128 GiB主要为T01完整单细胞任务及其中间对象预留空间。
该任务的代码门槛是64 GiB，完整运行峰值尚未实测。
这份配置建议采用按需付费，使用窗口结束后可以停止计算。
14天是首轮预算窗口，完整实验工期需在云上预跑后估计。

[实例官方规格](https://aws.amazon.com/ec2/instance-types/x8i/) · [物理核心与线程数](https://docs.aws.amazon.com/ec2/latest/instancetypes/mo.html)。

## B 哪个实验需要大内存：主要是T01完整单细胞

```callout info 128 GiB主要为T01留余量
T01使用完整975275个细胞、36027个基因。
单份核心稀疏数组推算约14.65 GiB。
本次将其工作内存按40—60 GiB作保守预算。
64 GiB是现有代码门槛；128 GiB是选机余量。
```

下表估计单个任务串行执行时的工作内存，不是RDS文件大小。
预算涵盖输入、中间对象和R运行开销；不是已经测得的完整峰值。

| 任务 | 工作内存预算（GiB） | 主要占用或现有证据 |
|---|---:|---|
| **T01 完整单细胞免疫组成** | **40—60** | **最大内存来源；完整稀疏矩阵、质控临时对象和转换副本** |
| T02 临床生存 | 2—4 | 数据表很小；已记录的进程树RSS峰值约1.02 GiB |
| T03 转录组差异表达 | 4—8 | 原始计数、归一化及拟合对象；未完成预跑记录约3.01 GiB进程树峰值 |
| T04 人群遗传 | 4—8 | 2504人×5000—10000个SNP；基因型副本、标准化与PCA |
| T05 GWAS功能解释 | 8—32 | 大型汇总表、字符串、注释及排序副本；真实规模仍待制备核对 |
| T06 ATAC调控 | 4—8 | 区间表、基因注释和富集计算；按当前处理后数据方案估计 |
| T07 蛋白候选设计 | 4—8 | 149360个变体、特征矩阵和交叉验证对象；规划估计 |
| T08 蛋白组差异 | 4—8 | 蛋白矩阵、缺失处理和拟合对象；规划估计 |
| T09 代谢组预测 | 2—4 | 968×189的代谢物矩阵及验证对象；规划估计 |
| T10 空间转录组 | 8—16 | 3813个spot、表达矩阵、空间距离与邻域对象；规划估计 |

T01以外的范围用于安排机器，仍需用完整预跑的峰值替换。
十项任务按顺序运行，不能把十行预算直接相加。
目前没有证据表明某项实验必须占满128 GiB。

## C T01的内存预算怎样得到

```flow LR
完整单细胞数据 -> 单份稀疏数组约15GiB: 数值与索引
单份稀疏数组约15GiB -> 原始与临时对象同时存在: 质控和转换
原始与临时对象同时存在 -> 工作预算40至60GiB: 保守估算
工作预算40至60GiB -> 128GiB主机: 系统与未测峰值余量
```

| 层次 | 数字的含义 |
|---|---|
| 完整来源规模 | 975275个细胞、36027个基因，约13.1亿条非零表达值 |
| 一份核心数组 | 数值每条8字节、行索引每条4字节，加列指针，合计约14.65 GiB |
| 工作内存40—60 GiB | 按2—3份大数组量级的保守场景，加元数据和R开销估计 |
| 64 GiB | 运行器检查的物理内存下限，不是完整任务的实测峰值 |
| 128 GiB | 本次主机规格建议，目的是给内存波动留下空间 |

这个预算假设沿用现有稀疏算法，不把整个矩阵转成普通稠密矩阵。
完整稠密double矩阵单份约262 GiB，属于另一种内存需求。
若只做T02—T10，128 GiB并非目前已证明的必要条件。
如果希望尝试64 GiB，应先用完整T01验证峰值再定正式配置。

源规模取自清单中的source_*字段。
清单的selected_cells=100000属于旧诊断子集，不是本次正式目标。
T01制备代码会检查正式输入是否保留全部975275个细胞。

[稀疏矩阵构造代码](../../prepare-single-cell.R) · [运行器内存预留与64 GiB门槛](../../v04.py) · [内存推算依据](AWS-MEMORY-v1.zh-CN.json)。

## D 少核方案比较：重点保留128 GiB内存

| 机型 | vCPU / 物理核 | 内存 | Linux按需单价 | 选择判断 |
|---|---:|---:|---:|---|
| x8i.xlarge | 4 / 2 | 64 GiB | $0.43766/小时 | 达到T01代码下限，但内存余量较小 |
| x2iedn.xlarge | 4 / 2 | 128 GiB | $0.83363/小时 | 更少核心的备选；使用较早的Intel平台 |
| x8i.2xlarge | 8 / 4 | 128 GiB | $0.87532/小时 | 推荐；Intel Xeon 6平台，物理核心仍只有4个 |

推荐机型相较4 vCPU的旧机型，每周计算费仅多约7美元。
如果希望严格压到4 vCPU，可选择x2iedn.xlarge。
申请数量固定为一台，表中是相互替代的选项。

规格来自[AWS实例文档](https://docs.aws.amazon.com/ec2/latest/instancetypes/mo.html)。
价格来自[AWS北弗吉尼亚Linux公开价表](https://b0.p.awsstatic.com/pricing/2.0/meteredUnitMaps/ec2/USD/current/ec2-ondemand-without-sec-sel/US%20East%20(N.%20Virginia)/Linux/index.json)。
本次读取的价格目录发布时间为2026-10-29。

## E 给IT的具体配置单

| 项目 | 建议配置 |
|---|---|
| 数量、区域 | 1台；us-east-1北弗吉尼亚 |
| EC2 | x8i.2xlarge，8 vCPU、128 GiB |
| 系统 | Ubuntu 24.04 LTS，x86_64架构 |
| 付费方式 | Linux On-Demand，共享租户 |
| 系统盘 | 100 GiB EBS gp3，默认性能 |
| 数据盘 | 2048 GiB（2 TiB）EBS gp3 |
| 数据盘性能 | 3000 IOPS，250 MiB/s吞吐 |
| 模型入口 | 云主机上重新认证Codex，固定GPT 6.1 SOL／low |
| 任务方式 | 一次一个任务、一个对照组；固定相同BLAS线程设置 |

```flow LR
本地VS Code -> 一台AWS主机: SSH管理
一台AWS主机 -> gp3数据盘: 数据与实验记录
一台AWS主机 -> 远程GPT服务: 模型调用
一台AWS主机 -> HTML报告: 结果与时间线
```

2 TiB为原文件、RDS、结果和失败现场预留空间。
这是存储容量预算，不是已测得的实际占用。
数据盘250 MiB/s约为262 MB/s。
这低于该机型312.5 MB/s的默认持续EBS带宽。
标称带宽不能直接当作RDS实测读取速度。

[实例EBS带宽](https://docs.aws.amazon.com/ec2/latest/instancetypes/mo.html) · [gp3性能规则](https://docs.aws.amazon.com/ebs/latest/userguide/general-purpose.html)。

## G 拿到机器后怎样开始

```timeline
1 | 配额与环境 | IT确认X实例额度，安装并记录R、依赖、Codex与BLAS版本
2 | 完整任务预跑 | 检查T01峰值内存及T03计算时间，确定线程与超时设置
3 | 冻结实验条件 | 在这台AWS机器上重新冻结数据、模型、环境和运行参数
4 | 顺序正式运行 | 同一台机器逐项完成任务，每项结束汇报并生成HTML
```

AWS默认配额表中，On-Demand X实例的额度为0。
本账号额度尚未查询，需由IT确认us-east-1可用额度至少8 vCPU。
该区域支持X8i；具体可用区的库存需在开机时确认。

T02已有的Mac结果保留为历史记录，AWS正式对比应在新环境重跑。
中断的Mac预跑不跨环境接着计时。
本页是资源申请建议；当前实验仍保持暂停。
