## A 摘要与研究背景

```callout info 本文主案例：A1第2次运行与C1第3次运行
A1用时61.85秒，C1用时72.69秒，均正确完成任务。
本案例相差10.84秒，A1总时长低14.9%。
甘特图展示三轮请求与其中的执行步骤。
```

连续的数据分析通常包含检查、首次计算和条件修改。
前一轮已经加载的矩阵和质控结果，在下一轮仍然有用。
gptr将分析对象保留在R会话中。
普通coding agent则可以通过脚本和文件组织连续工作。
本实验比较这两种工作流在真实数据任务上的表现。

核心问题是：同一模型完成相同分析时，整条工作流花费多少时间？
固定步骤实验进一步观察执行方式带来的成本。
真实轨迹回放则检查模型实际生成的R操作能否重复完成任务。

全文先交代实验方法，再展开主案例，最后呈现完整结果。
主案例恰好对应两组中位数，其他四次真实运行放入补充表。
本篇只分析已有v0.3记录，没有新增模型试验。

## B 正式选用的数据集，以及要完成的分析任务

**正式选定的数据来自GSE236581公开单细胞数据集。**

这份数据记录了细胞中各个基因的表达计数。
公开完整数据集包含975275个细胞。
本轮从中选取100000个真实细胞，也就是10万个细胞。
每个选中细胞都保留全部36027个基因的数据。
五个实验组使用这一份相同的数据。

```flow LR
公开数据975275个细胞 -> 正式选取100000个细胞: 按固定索引选取
正式选取100000个细胞 -> 保留全部36027个基因
保留全部36027个基因 -> 五个实验组共用
```

因此，975275表示公开完整队列的细胞数。
100000表示这次实际运行实验的细胞数。
本轮没有对完整队列测量性能，因为本机内存预检未通过。
选中的细胞及其表达计数均来自公开数据，没有模拟或复制。

**这份数据里具体存了什么？**

```tree
正式选用的10万细胞数据集
  基因表达矩阵 | 36027行基因 × 100000列细胞
  细胞说明表 | 每个细胞的编号、所属患者、组织和治疗时点
  基因说明表 | 每个基因的编号和名称
```

表达矩阵中的一个单元格，对应一个细胞中的一个基因。
其中的数字表示观测到的表达计数。
部分单元格为零，表示该位置没有检测到表达计数。

| 数据统计内容 | 数值 | 这个数字说明什么 |
|---|---:|---|
| 正式实验使用的细胞数 | 100,000 | 实验实际分析的细胞数量 |
| 基因数 | 36,027 | 每个细胞都保留的基因范围 |
| 有表达计数的单元格数 | 134,275,503 | 表达矩阵中计数大于零的位置数量 |
| 表达计数总和（UMI） | 377,073,775 | 将矩阵里的表达计数全部相加 |
| 覆盖的患者数 | 22 | 这些细胞来自22位患者 |
| 覆盖的原始样本数 | 169 | 这些细胞分布在169份原始样本中 |
| 后续分析分组数 | 168 | 按患者、组织和治疗时点组合后得到的组数 |

多个样本可以属于同一位患者。
同一患者、同一组织和同一时点的样本会合并分析。
因此，169份样本对应168个分析组。

**数据有多大，保存在哪里？**

上述矩阵和两份说明表一起保存为R数据文件 `input.rds`。
文件大小为1636075918字节，约1.64 GB。
矩阵采用稀疏格式，主要存储有计数的位置及其数值。
这能减少大量零值带来的存储负担。

这里的1.64 GB是数据文件大小。
程序运行时的内存占用另在F节报告。
本地数据文件位于 `data/gse236581-100000/input.rds`。

**拿到这份数据后，连续完成三轮分析。**

```flow LR
请求1检查与质控 -> 请求2首次汇总: 保留细胞质控结果和分组
请求2首次汇总 -> 请求3修改阈值: 复用数据集和质控结果
```

质控就是检查数据质量。
本任务为每个细胞计算表达计数总和，以及有表达的基因数。
随后使用这两个指标筛选细胞，再按组汇总表达量。

| 请求 | 具体做什么 | 产生什么结果 |
|---|---|---|
| 1：检查与质控 | 核对编号和矩阵维度；计算每个细胞的两个质控指标 | qc.csv记录整体统计；cell-qc.csv记录10万个细胞的指标 |
| 2：首次汇总 | 保留表达计数总和≥1000、检测基因数≥500的细胞；汇总全部基因 | 保留99125个细胞，写出baseline.csv |
| 3：提高阈值 | 将两项条件提高到2000和1000；重新汇总全部基因 | 保留69684个细胞，写出revised.csv |

两次汇总均先计算全部基因，再提取八个标记基因。
每份表达结果包含168组×8个标记，共1344行。
每行报告细胞数、全基因总计数、标记计数及标准化表达量CPM。
空组也必须保留。

**原始下载文件怎样变成RDS？**

公开网站提供的是压缩矩阵和说明表，原文件不是RDS。

| 下载文件 | 保存的内容 |
|---|---|
| GSE236581_counts.mtx.gz | Matrix Market格式的原始表达计数矩阵 |
| GSE236581_barcodes.tsv.gz | 细胞编号 |
| GSE236581_features.tsv.gz | 基因编号与名称 |
| GSE236581_CRC-ICB_metadata.txt.gz | 细胞所属患者、组织和治疗时点 |

```flow LR
下载四个压缩文件 -> 分块读取并选取10万细胞
分块读取并选取10万细胞 -> 对齐矩阵与两份说明表
对齐矩阵与两份说明表 -> 保存为input.rds
保存为input.rds -> 五组分别加载并分析
```

这一步预处理只做细胞选取、数据对齐和存储格式整理。
选中细胞的原始表达计数保持不变。
任务要求的质控指标和表达汇总没有预先算好。
RDS在正式计时前准备；各组加载RDS的时间仍计入实验。

**这些分析在什么环境中运行？**

| 实验条件 | 本轮采用的配置 |
|---|---|
| 模型 | GPT 6.1 SOL，显式指定gpt-6.1-sol |
| 模型入口 | 两个真实组均使用Codex CLI 0.165.0 |
| 思考强度 | 未显式覆盖；本机模型目录的默认值为low |
| 用户配置 | 实验命令忽略用户配置，不采用全局的思考强度设置 |
| 执行环境 | macOS arm64、32 GiB物理内存、R 4.5.1 |
| 主要数值依赖 | Matrix 1.7.3 |
| 执行安排 | 串行运行；A1/C1先后顺序交替 |

这里的low来自本次核对的Codex模型目录。
原实验清单只记录“模型默认”，未保存最终解析出的强度值。
[模型配置核对记录](REPORT-v0.3-model-settings.zh-CN.json)保留了目录与会话依据。

## C 五组对照与计时方法

**真实组比较完整工作流，固定组比较相同计算的执行方式。**

```flow LR
同一数据集与任务 -> 真实模型生成代码
同一数据集与任务 -> 预先固定R计算
真实模型生成代码 -> A1真实gptr
真实模型生成代码 -> C1真实Codex
预先固定R计算 -> A2实际gptr循环
预先固定R计算 -> C2逐步新R进程
预先固定R计算 -> C3一次R批量执行
```

| 组别 | 执行方式 | 是否真实模型 | 本组回答什么 |
|---|---|---|---|
| A1 | Codex经gptr桥接，使用常驻R会话 | 是 | gptr完整交互工作流的表现 |
| C1 | Codex自行组织脚本、命令和状态文件 | 是 | 普通coding agent完整工作流的表现 |
| A2 | fake回复驱动实际gptr循环 | 否 | 保留gptr机制后的重复执行成本 |
| C2 | 相同计算分三步，每步启动新R并恢复RDS | 否 | 分步进程与状态文件的成本 |
| C3 | 一个R进程连续执行相同三步 | 否 | 合并执行的批量基线 |

C1可以自主选择脚本和文件组织方式。
它没有被强制采用C2协议。
每次独立试验都使用新会话、新工作目录和同一份数据集。
同一次试验中的三个用户请求连续进行。

**计时覆盖完整响应过程。**

```flow LR
下载准备与工作区复制 -> (计时开始)
计时开始 -> 启动与加载
启动与加载 -> 三轮模型和工具交互
三轮模型和工具交互 -> 最终回复及进程收尾
最终回复及进程收尾 -> (计时结束)
计时结束 -> 独立结果检查
```

CSV写出后，最终文本回复和子进程退出仍在计时内。
正常权限处理与agent运行开销也包含在总时长中。
下载、数据准备、工作区复制和独立检查在计时外。
内存按20毫秒间隔采样进程树RSS。
系统缓存没有强制清空。

查证：[计时及编排](../../run.py) · [R执行器](../../runner.R)。

## E 大文件读取与工具执行：10.84秒的差额落在哪里

**这份约1.64 GB的大文件，读取一次要多久？**

正式A1-2对 `readRDS()` 单独计时，结果为 **2.334秒**。
它发生在用户请求1之前，已经计入61.85秒总时长。
之后的质控与两次汇总直接复用会话对象。
因此，质控R调用的3.095秒没有再次包含大文件读取。

**C1也读取数据，只是读时融入了各条R命令。**

| 运行环节 | A1-2 | C1-3 |
|---|---|---|
| 请求之前 | 一次读取，独立计时2.334秒 | CLI启动；尚未进入R分析 |
| 请求1：结构检查 | 使用已加载对象 | R1读取一次；包含在2.572秒命令中 |
| 请求1：计算质控 | 继续使用同一对象 | R2再读一次；包含在6.084秒命令中 |
| 请求2：首次汇总 | 复用数据与QC | R3再读一次；包含在5.578秒命令中 |
| 请求3：提高阈值 | 复用数据与QC | R4再读一次；包含在5.380秒命令中 |
| **原始大文件读取次数** | **1次** | **4次** |

图1新增金色框，标出C1包含大文件读取的四条命令。
框长是整条命令的时长，不能当作读取本身的时长。
原C1没有为 `readRDS()` 单独打点，所以每次独立读时未记录。
这些读取都已包含在72.69秒总时长中。

**补充测量：同一文件在五个新R进程中分别读取一次。**

```chart bar horizontal unit=s
补测1 | 2.451
补测2 | 2.587
补测3 | 2.280
补测4 | 2.000
补测5 | 1.903
```

五次补测中位数为 **2.280秒**。
耗时范围为 **1.903—2.587秒**。
只计 `readRDS()` 恢复R对象的过程，R进程启动不在该计时内。
这说明当前条件下，一次读取大致需要两秒左右。

补测在报告修订时执行，与原66次正式执行分开保存。
系统缓存未清空，测前也读取过文件以核对哈希。
这些数值不能追溯替代C1当时的四次独立读时。
读取时间也包含对象恢复，不能当作纯磁盘传输时间。

大文件读取优化应先关注是否需要反复恢复同一份数据。
本案例A1读一次，C1读四次，重复读取的位置已可直接查看。

查证：[五次读取补测](REPORT-v0.3-read-probe.zh-CN.csv) · [方法、文件哈希和环境](REPORT-v0.3-read-probe.zh-CN.json) · [补测R脚本](REPORT-v0.3-read-probe.zh-CN.R)。
