## A 把它看成十道考试题的配套材料
| 考试中的东西 | 当前文件位置 |
|---|---|
| 题目：让模型做什么 | prompts.json |
| 参考答案：人工预写的分析代码 | tasks/v04/里的T01–T10模块 |
| 评分规则：结果怎么算通过 | 同一批模块中的check函数 |
| 开始考试：调用模型作答 | shared/runner.R调用peter；shared/run.py调用Codex |

T01–T10是十个科研任务的编号。
它们不是十个Peter启动脚本。

## B 每个任务模块实际提供什么
| 内容 | 程序拿它做什么 |
|---|---|
| artifacts：应生成哪些文件 | 实验结束后核对产物 |
| steps：人工写好的R计算步骤 | 给离线对照组执行 |
| request、reads、writes | 标记步骤属于哪轮，哪些对象需要跨轮保存 |
| check函数 | 检查生成的CSV和统计结果 |

T01刚拆成三个文件：
```tree
T01
  t01.R | 产物清单、分轮与对象依赖
  t01-analysis.R | 人工参考答案
  t01-check.R | 评分规则
```
T02–T10仍把这些内容放在各自的一个R文件中。
题目的文字已经统一移到prompts.json。

## C 真实模型和离线对照怎样使用它们
```flow LR
[prompts.json里的题目] -> [A1：peter调用真实模型]
[A1：peter调用真实模型] -> [模型自己写代码并生成结果]
[模型自己写代码并生成结果] -> [任务检查器评分]
[tasks里的人工参考代码] -> [离线对照：A2、C2、C3]
[离线对照：A2、C2、C3] -> [任务检查器评分]
```
A1不会把人工参考代码当成模型答案执行。
A2也会调用peter，但使用fake provider喂入预定代码。
A2还可以使用已捕获的兼容轨迹，而非人工参考代码。
C2、C3直接执行代码，用于比较进程和状态保存开销。

```callout info 你觉得名称不直观是有原因的
当前tasks把参考答案、离线执行信息和评分规则混在一起。
它的职责比“任务入口”更杂，所以打开T01看不到peter调用。
```
